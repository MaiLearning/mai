# Sync — автоматическая синхронизация данных (frontend ↔ backend)

> **Статус миграции.** Механизм перенесён в пакет `@mai/sync` (этот каталог).
> Портированы точки подключения: таска `src/app/runner/task/init_events.ts`
> (зарегистрирована в `src/app/app.tsx`) и appliers
> `course` (`@mai/course`), `structure` + `directory` (`@mai/structure`),
> `resource` + `resourceType` (`@mai/resource`), `plugin` (`@mai/plugin`),
> `link` (`@mai-plugin/link`). Не портированы: Rust-издатель событий
> (`src-tauri/src/services/events.rs`). Настройка fake-режима — в едином
> конфиге `@mai/config`: таска `initConfigTask` вызывает `configureFakeData`
> с данными `mai.toml`. Документ описывает механизм в том виде, в котором он спроектирован и
> работал в предыдущем поколении фронтенда (`app/_mai`).

Как изменения данных доезжают до интерфейса без перезагрузки и ручных обновлений.
Механизм живёт в `src/packages/sync/` — это инфраструктура приёма событий, а не сущность.
Связанный документ: `src/entities/ENTITIES.md`.
Требования к авторам эндпоинтов/доменов (что обязан реализовать для синхронизации) —
`src-tauri/src/server/endpoints/ENDPOINTS.md`.

## Зачем

Данные приложения могут меняться не только из интерфейса, но и через HTTP API
(внешние агенты, скрипты — Axum-сервер в `src-tauri`). Все мутации проходят через
сервисный слой Rust-бэкенда; сервис после успешной мутации публикует событие,
фронтенд получает его и перечитывает затронутые данные. Вторая роль той же
механики — согласованность внутри фронтенда: все фичи читают и пишут данные
только через сторы сущностей (см. `src/entities/ENTITIES.md`), поэтому
обновление атома автоматически перерисовывает все зависимые компоненты
(например, дерево курса и редактор узла).

## Модель v1 (текущая): сигнал + refetch

Событие — только сигнал «что изменилось», без самих данных:

```json
{
  "entity": "course | structure | directory | resource | resourceType | plugin",
  "action": "created | updated | deleted",
  "id": "…",
  "courseId": "… | null",
  "origin": "ipc | http",
  "timestamp": 1756800000000
}
```

| Слой | Где | Роль |
|------|-----|------|
| Контракт | `src-tauri/src/services/events.rs` | типы + трейт `ChangePublisher` (сервисы не знают про Tauri) |
| Доставка | `src-tauri/src/utils/events.rs` | `TauriChangePublisher` → `emit("entity://changed")` |
| Публикация | сервисы `course`, `structure`, `resource` (ресурсы и их типы), `plugin` | `publisher.publish(...)` после успешной мутации |
| Приём + реестр | `src/app/runner/task/initEvents.ts` | одна подписка `listen('entity://changed')`; собирает реестр «сущность → applier» из атомов сущностей; включает межпакетные подписки `@mai/bus` |
| Маршрутизация | `src/packages/sync/` | Zod-валидация payload, диспетчер `createEventDispatcher` без знаний о сущностях |
| Применение | `src/packages/<name>/src/store/sync.ts` | refetch через существующие load-атомы |
| Межпакетные сигналы | `src/packages/bus/` (`@mai/bus`, nanoevents) | фронт ↔ фронт: пакеты публикуют факты (`'resource/changed'`), не импортируя друг друга; подписки включает композиция (init-events). Каталог событий — `src/packages/bus/BUS.md` |

Правила v1:

- **`origin=ipc` игнорируется.** Мутацию инициировал сам фронт — он уже обновил
  свои сторы в action atoms. Повторный refetch избыточен и может гоняться
  с optimistic-мутациями structure. Обрабатываются только `origin=http`.
- **Применение — штатными средствами.** Appliers вызывают существующие
  load-атомы, значит данные проходят обычную Zod-валидацию сервисов.
  Отдельного «второго» пути разбора данных на фронте нет.
- **Двойные события.** Операция над папкой публикует и `Directory`, и
  `Structure` (дерево и список папок — разные сторы). Два refetch вместо
  одного — приемлемая цена простоты v1.
- **Ресурсы видны через дерево.** Список ресурсов (`resourcesAtom`) не
  имеет загрузчика и потребителей — реакция на Resource-события:
  `applyResourceChangeAtom` публикует факт `'resource/changed'` в `@mai/bus`,
  подписанный `@mai/structure` перечитывает дерево курса (если оно открыто,
  через `refetchStructureIfLoaded`). Ресурс виден в UI именно в узлах дерева
  (встроенный payload). Прямой зависимости `resource → structure` нет —
  пакеты связаны только через шину.
- **Плагины/типы ресурсов** — глобальные списки, refetch без guard.
- **Конфликты:** last-write-wins по `updatedAt`, как и раньше.
- **Ошибки доставки** не влияют на результат мутации (fire-and-forget).
- **Fake-режим** (`isFakeDataEnabled`): подписка не ставится — данные меняет
  только фронт, SSOT консистентен и так.
- **Механизм — инфраструктура, не сущность.** `packages/sync` не импортирует
  сущности: реестр appliers передаётся снаружи (`createEventDispatcher`
  в init-events). Новая сущность = её applier + одна запись в реестре.

## Лестница оптимизации (v1 → v2 → v3)

| Ступень | Payload | Фронт | Цена на событие |
|---------|---------|-------|-----------------|
| **v1 (сейчас)** | сигнал | refetch load-атомами | +1 запрос |
| **v2 — upsert** | готовый объект (например, `Course` целиком) | мерж в атомы через Zod, без refetch | только событие |
| **v3 — diff** | только изменённые поля `{changed: ["name"], name: "…"}` | точечный патч атомов | минимум |

- **v2 upsert.** Сервис и так возвращает сохранённый объект — приложить его
  к событию и мержить в сторы (валидация Zod-схемами сущностей). Убирает
  refetch для простых сущностей; для structure остаётся refetch — дерево
  собирается на фронте из плоских узлов.
- **v3 diff.** Rules-валидация сервисов уже идёт по полям — сервис знает,
  какие поля менял. Событие несёт только их; фронт патчит атомы точечно.
  Максимальная экономия, самая строгая парность схем.

**Когда переходить:** v2 — при заметном трафике refetch (частые обновления
от агентов, длинные списки); v3 — при больших деревьях/контенте либо в
daemon-фазе (SSE-транспорт, см. TODO в `src-tauri/src/startup.rs`), где
каждый байт доставки дорог.

## Риски и защита

- **Пропуск событий** (перезагрузка webview, ошибка доставки): события —
  оптимизация, а не единственный источник истины. При старте фронт
  загружает данные штатными load-атомами, так что пропущенное событие
  самоликвидируется при следующем открытии экрана.
- **Порядок доставки**: v1 нечувствительна (refetch всегда возвращает
  актуальное состояние). Для v2/v3 ввести монотонный счётчик событий
  и отбрасывать устаревшие.
- **Парность схем** Rust serde ↔ Zod: контракт закреплён тестом с двух
  сторон — `utils/events.rs::payload_uses_camel_case_keys` (Rust) и
  `packages/sync/src/protocol.ts` (Zod). Контракт менять только парно.

## Вне рамок v1

- `kv` / `task` / `theory` — по мере появления HTTP-эндпоинтов.
- SSE/WebSocket-транспорт для daemon-сценария — TODO в
  `src-tauri/src/startup.rs`; шина (`ChangePublisher`) транспорт-агностична.

## Известные ограничения

- **Удаление ресурса через HTTP не удаляет его узел структуры**
  (pre-existing поведение домена resource): `DELETE /resources/{id}`
  удаляет запись и директорию ресурса, но узел дерева остаётся — после
  refetch дерево покажет узел-сироту. Целостность structure↔resource
  — отдельная задача, не событийная.
- `add_internal` (регистрация internal-плагинов на старте) не публикует
  событий — слушателей ещё нет.
