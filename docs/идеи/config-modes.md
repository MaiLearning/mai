# Конфигурация бэкенда через mai.toml

Статус: БД реализована, сервер остаётся идеей · Зависимости: [пакет @mai/config](../../src/packages/config/docs/README.md)

## Зачем

Раньше БД-часть backend-а конфигурировалась собственными механизмами
(`database::sqlite::settings`, учёт dev/prod). Единый `mai.toml` стал связующим
звеном для фронта и бэкенда: backend читает из него путь и параметры SQLite.

## Что делаем

Выносим из внутренней конфигурации бэкенда параметры, которые зависят
от режима, и объявляем их вложенными секциями режима:

```toml
[mode.development]
debug = true
fake_data = true
hot_reload = true

[mode.development.database]
path = ".dev/mai_dev.db"
max_connections = 5
```

Каждый режим может расширяться по внутренним функциям (server, database, …).
Кроме того — независимые от режима модули:

```toml
[application]
window_width = 1280
window_height = 800
```

Ожидаемый эффект:
- один источник правды для всей конфигурации проекта;
- выбор `.dev`/`.release` директорий и портов без правки Rust-кода;
- настройки окна (dimensions) — объявлением, а не хардкодом.

## Открытые вопросы

- Секции сервера и других backend-подсистем.
- Согласование frontend-режима из `mode.default` с профилем backend-сборки.

## Прогресс

- [x] Конфигурация SQLite перенесена в `mai.toml`.
- [x] Относительный путь разрешается от `app_data_dir`.
- [x] Backend выбирает режим по профилю debug/release и валидирует секцию до запуска пула.
- [ ] Перенос HTTP-сервера в `mai.toml`.
- [ ] Горячее пересоздание пула БД при изменении конфигурации.
