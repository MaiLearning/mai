

1. `pnpm --filter @mai/utils add @mai/ui --workspace` - устанавливает пакет ui в пакет utils, по аналогии с этой командой ты всегда должен именно так добавлять зависимости из одного пакета в другой.
2. Именование файлов: внутри app/mai все файлы — camelCase (хуки `useXxx.ts`, прочие — `descriptiveName.ts/tsx`); компоненты — PascalCase; стили — парные `<Name>.style.ts`. kebab-case и snake_case не используются.
4. Настройки — пользовательские (`src-tauri/src/services/settings` + пакет `@mai/settings`), не путать с `config` (mai.toml, для разработчика) и `kv` (сервисное хранилище). Модель: документ на пункт `(domain, itemId)`, домены `system`/`plugin`/`course`, типы полей — реестр схем на Rust (`schemas/`), валидация значений на бэкенде. Системные «Общие» (`system/general`): `theme` + `language` описываются тем же `definePluginSettings` (`systemSettingsDefinition`) и рендерятся той же формой, что plugin settings; применяются реактивно в `src/app/app.tsx` (ThemeProvider) и таской `init_settings` (i18n). Дефолты — в Zod-схеме определения, в БД пункт пишется при первом изменении. IPC: `settings_get/update/delete` (`client/command/settings.rs`).
5. Настройки описываются Zod-схемой через `definePluginSettings` (`jsonSchema` — из `z.toJSONSchema()`); состояние пункта живёт в общем сторе `@mai/settings` по ключу `domain:itemId` (переживает уход со страницы и связывает потребителей: форма настроек и viewer плагина видят одни значения). UI рендерится по `settingsFieldSpecs` (self-describing `SettingsField` → `SettingsFieldRenderer`), подписи/пояснения/варианты выбора берутся по конвенции ключей `<поле>.label|.hint|.options.<значение>` в namespace определения, запись — автосохранение с паузой (`SETTINGS_AUTOSAVE_DELAY`); статус сохранения — инлайн, ошибки/конфликты — тостом `@mai/notifications`. Потребитель настроек не только фронтенд: бэкенд-плагин читает свой пункт через `SettingsService` (пример — code берёт пути рантаймов, интерпретаторов Python/JavaScript и компилятора Rust `rustc`, из `plugin/internal-code`); ключи полей при этом — осознанное зеркало Zod-схемы. Миграции пока сознательно не реализуются; несовместимые изменения требуют сброса настроек.
6. SQLite-конфигурация (`path`, `max_connections`) задаётся в `mai.toml` в секциях `[mode.<имя>.database]`; backend выбирает `development` в debug и `release` в release. Относительный `path` разрешается от `app_data_dir`, а изменение файла не пересоздаёт пул до перезапуска.
7. MCP-сервер для ИИ-агентов — `src-tauri/src/server/mcp/`, см. **`server/mcp/MCP.md`** (соглашения слоя, чек-листы, грабли — по образцу `server/endpoints/ENDPOINTS.md`). Ключевое: агент платит токенами за каждый ответ, поэтому отдаём проекции (`dto.rs`: `brief` по умолчанию, `full` по запросу), **только компактный JSON** (никакого `to_string_pretty`), ограничения явными параметрами (`maxNodes`/`maxResults`), а не молчаливой обрезкой. Оглавление курса — **текстовое дерево** (`render/outline.rs`), не JSON. Содержимое ресурса — по `typeKey` через проекции `content/`; `format: "text"` безвозвратен (теряет `callout`/`formula`/`embed`/`wikiLink`/подсветку), поэтому для любой правки нужен `format: "json"`. Формат контента теории — **TipTap (ProseMirror JSON), не Lexical**: пустое состояние задаёт `empty_doc()` в `plugins/theory/service/service.rs` и обязано совпадать с `emptyDoc()` во фронте. Слой read-only: не мутирует БД, ошибки отдаются результатом с `isError`, а не JSON-RPC ошибкой. Инструкции агенту — `instructions.md` + `include_str!`; длинные справки — MCP-ресурсы `mai://guide/*`; `get_info` пишется вручную (см. MCP.md).
