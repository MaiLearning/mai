# MCP — доступ для AI-агентов (`src-tauri/src/server/mcp`)

Соглашения реализации MCP-слоя. Монтируется в общий Axum: `nest_service("/mcp", …)`
в `server/router.rs`. Слой **поверх** service layer: инструменты зовут те же
сервисы, что Tauri-команды и HTTP-эндпоинты, — бизнес-логика живёт только в
`services/`.

Транспорт: streamable HTTP, режим stateless — сессий нет, каждый запрос
самодостаточен (`NeverSessionManager`), ответ JSON вместо SSE. На запрос
фабрика собирает свежий `MaiMcpServer`: клон состояния дёшев (Arc), сервисы
собираются per-call по образцу HTTP-эндпоинтов.

## Три примитива MCP

- **Инструмент** (`tools/`) — модель вызывает сама: аргументы → результат.
- **Ресурс** (`resources/`) — данные по URI: модель решает, что и когда читать.
- **Инструкция** (`instructions.md`) — попадает в контекст агента всегда.

Справочная документация — это ресурсы, а не инструменты: инструмент означал бы
вызов агента только чтобы прочитать справку к себе.

## Структура каталога

```
mod.rs           транспорт + объявления модулей
handler.rs       MaiMcpServer { state }
router.rs        маршруты инструментов, get_info, list_resources/read_resource
render.rs        рендер ответов: компактный JSON, кап, метрики
render/outline.rs  текстовое дерево структуры курса
dto.rs           проекции доменных моделей (brief/full)
instructions.md  текст, отдаваемый агенту в initialize
content/         проекции содержимого по typeKey  (не путать с resources/)
resources/       MCP-ресурсы mai://guide/*         (не путать с content/)
tools/           по файлу на инструмент
```

Три точки регистрации нового инструмента:

1. `tools/mod.rs` — объявление модуля;
2. `tools/<name>.rs` — `Args` + логика в `run(state, args)`;
3. `router.rs` — маршрут с `#[tool(description = …)]`, вызывающий `run`.

Описание инструмента живёт в `router.rs`: атрибут макроса принимает только
строковый литерал, вынести его в `tools/` нельзя. Doc-комментарии на полях
`Args` попадают в JSON-схему параметров — их писать обязательно.

## Шаблон инструмента

```rust
//! `mai_get_thing` — короткое назначение инструмента.

use rmcp::model::CallToolResult;
use rmcp::ErrorData;
use schemars::JsonSchema;
use serde::Deserialize;

use crate::server::state::AppState;

use super::super::render;

pub const NAME: &str = "mai_get_thing";

#[derive(Deserialize, JsonSchema)]
#[serde(rename_all = "camelCase")]
pub struct Args {
    /// Что означает поле — попадёт в схему параметров
    pub thing_id: String,
}

pub async fn run(state: &AppState, args: Args) -> Result<CallToolResult, ErrorData> {
    let service = /* … */;

    match service.get(&args.thing_id).await {
        Ok(data) => render::json(NAME, &data),
        Err(e) => render::tool_error(NAME, e),
    }
}
```

Правила:

- **Никакой сериализации в инструменте** — только вызов `render::json` или
  `render::text`. Рендер единственная точка, где считается бюджет ответа.
- **Имя — с префиксом `mai_`**: `mai_list_courses`, `mai_get_resource`.
  Префикс отделяет инструменты Mai от прочих в каталоге клиента.
- **Доменные модели наружу не отдаются** — они контракт приложения и HTTP
  (их же ест utoipa) и нужны там в полном виде. Агенту отдаются проекции из
  `dto.rs`.
- **Уровни детализации: `brief` по умолчанию, `full` по явному запросу.**
  Пикер полей (`fields: […]`) не используется: агент выбирает набор неверно и
  повторяет вызов, один переключатель `detail` предсказуем.
- **Только компактный JSON.** `to_string_pretty` на вложенных объектах даёт до
  +30% чисто пробельного мусора.
- **Никогда не обрезать молча.** Списки ограничиваются постраничностью или
  `maxNodes`, а `render::text` режет по границе символа и дописывает хвост с
  подсказкой. Обрезанный посередине JSON нечитаем — режутся только тексты.
- **Ошибки actionable.** `render::tool_error` получает не только текст ошибки
  сервиса, но и что делать дальше («посмотри оглавление целиком», «известны:
  …»).
- **Описание инструмента объясняет формат, а не пересказывает имя**: значения
  enum, единицы, что исключено, что вызвать следующим.
- **Метрики бесплатно**: `render` логирует символы и оценку токенов на каждый
  вызов. Оптимизация токенов без измерения — гадание.

## Оглавление курса — текстом, не JSON

`mai_course_outline` отдаёт дерево текстом, одна строка на узел: отступ = глубина,
`[dir <id>]` или `[res <id> <typeKey> upd:<мс>]`. Причина — форма, а не вкус:
вложенный JSON с отступами стоит в разы дороже, а модель такую форму читает
лучше всего (оглавление, вывод `ls` сильно представлены в обучении). Плоский
список с `parentId` для этого не годится: на 50+ узлах родители склеиваются
ненадёжно.

Ограничения — параметры инструмента, а не молчаливое обрезание: `rootId`
(поддерево или путь от корня), `depth`, `typeKeys`, `maxNodes`. Исчерпание
`maxNodes` видно в ответе и сопровождается подсказкой.

Правила формата: только ASCII (`📁` стоит несколько токенов на каждом узле), id
всегда в скобках — агент копирует дословно. Размер контента в оглавлении **не
показывается**: он лежит в отдельных таблицах, и вычисление потребовало бы
выборки на каждый узел — ровно тех запросов, которых слой избегает.

## Проекции содержимого (`content/`)

Тип ресурса (`typeKey`) определяет, кто читает хранилище и как содержимое
превращается в текст. `mai_get_content` только маршрутизирует, поэтому новый
тип содержимого не трогает ни инструмент, ни его описание.

```rust
pub trait ContentView: Send + Sync {
    fn type_keys(&self) -> &'static [&'static str];
    fn label(&self) -> &'static str;
    fn fetch<'a>(&'a self, state: &'a AppState, resource_id: &'a str) -> Fetch<'a>;
    fn to_text(&self, raw: &Value) -> String;
}
```

Новый тип: реализация `ContentView` + статический экземпляр + строка в
`registry::all()`. `fetch` возвращает бокснутый future — трейт объектный
(`&'static dyn ContentView`), а хранилища асинхронные.

Форматы ответа: `text` — чтобы понять содержимое дёшево, `json` — чтобы работать
с документом без потерь. Текстовая проекция **безвозвратна**: `callout`,
`formula`, `embed`, `wikiLink`, подсветка и подчёркивание в текст не ложатся.
Поэтому она никогда не единственный путь: любая правка идёт через `json`.

## MCP-ресурсы (`resources/`)

Справочные документы под `mai://guide/`: `glossary` (термины, соответствие
`typeKey` плагинам), `workflow` (разобранные сценарии). Реестр — список
`(uri, name, description, body)`, тело встраивается через `include_str!`.

Макросов для ресурсов в rmcp нет — только ручные `list_resources` /
`read_resource`. Макрос `#[tool_handler]` при этом **сливается** с impl-блоком
и добавляет `call_tool` / `list_tools` / `get_tool` / `get_info` только если их
ещё нет, поэтому ресурсы живут в том же блоке `router.rs`.

## `get_info` пишется руками

`#[tool_handler(instructions = …)]` не используется по двум причинам:

1. атрибут принимает только строковый литерал, а инструкции лежат в
   `instructions.md` и встраиваются через `include_str!`;
2. макрос объявляет capability только `tools` — без `.enable_resources()`
   сервер не сообщит клиенту про ресурсы, и они останутся невидимыми.

Писать `get_info` вручную обязательно, чтобы объявить `enable_resources()` и
отдать инструкции. Атрибуты `name` / `version` / `instructions` при этом
становятся мёртвыми — макрос читает их только генератором `get_info`.

Разделение текстов: `instructions.md` — что делать и куда идти (агент читает
всегда), ресурсы `mai://guide/*` — как устроено подробно (читает по надобности).
Критичное не должно жить только в ресурсе: поддержка resources у клиентов
неравномерна, и агент может о них не узнать.

## Read-only инвариант

Инструменты **не мутируют БД** — ни своих строк, ни чужих. Отсюда:

- строгие `get`, а не `get_or_default`: отсутствие контента — это `not found`,
  а не повод создать пустой;
- `NEVER_SAVED = 0` в виртуальной записи — чтобы staleness-проверки клиента
  не приняли пустоту за свежие данные;
- несуществующий ресурс = `NotFound`, иначе опечатка в id выглядела бы
  «успехом» с пустым содержимым.

При появлении первой мутации: паблишер берётся из `state.publisher`
(`origin=http`), публикует **сервис** после успешной операции, инструмент
только передаёт паблишер. Событийный контракт — по `ENDPOINTS.md` и
`app/mai/src/utils/sync/SYNC.md`, синхронно с правкой Rust-части.

## Чек-лист: новый инструмент

- [ ] файл в `tools/` + объявление в `tools/mod.rs`
- [ ] `Args` с doc-комментариями на полях, `#[serde(rename_all = "camelCase")]`
- [ ] `run(state, args)` возвращает через `render::json` / `render::text`
- [ ] маршрут и `#[tool(description = …)]` в `router.rs`
- [ ] описание объясняет формат, enum-значения, что исключено, что дальше
- [ ] упоминание нового инструмента в `instructions.md`, если он часть маршрута
- [ ] тест на логику инструмента или на его проекцию (`dto` / `content` / `render`)
- [ ] `cargo fmt && cargo check && cargo clippy && cargo test`

## Чек-лист: новый MCP-ресурс

- [ ] документ в `resources/md/` (начинается с `# `)
- [ ] запись в `registry::all()` с уникальным URI
- [ ] при необходимости — строка-ссылка в `instructions.md`
- [ ] `cargo test resources` (тесты реестра проверяют уникальность URI и тела)

## Известные грабли

- **Формат контента теории — TipTap (ProseMirror JSON), не Lexical.** Имя
  `empty_lexical_state` и фраза «Lexical-состояние» в старых описаниях вели к
  тому, что в БД попадал документ, которого редактор не понимает. Пустое
  состояние задаёт `empty_doc()` в `plugins/theory/service/service.rs` и должно
  совпадать с `emptyDoc()` во фронте.
- **Разбор содержимого различает форму, а не версию.** В `theory_content` могут
  лежать строки, записанные старым Lexical-образным состоянием; проекция
  определяет документ по полям (как фронт в `isTipTapDoc`), а не по дате.
- **Содержимое конвертируется в текст только для чтения.** Правки идут через
  `format: "json"`: текстовая проекция теряет `callout`, `formula`, `embed`,
  `wikiLink`, подсветку и подчёркивание.
- **Ошибка инструмента — это результат с `isError`, а не JSON-RPC ошибка.**
  Агент должен увидеть текст и исправиться (взять другой id, сузить выборку),
  а не просто остановиться. JSON-RPC ошибка — протокольные неполадки:
  неизвестный инструмент, нечитаемые параметры.
